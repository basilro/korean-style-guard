# korean-style-guard

korean-style-guard는 AI 에이전트가 쓰는 한국어를 사람이 쓴 글처럼 읽히게 다듬는 플러그인입니다. Claude Code와 Codex CLI에서 작동합니다. 에이전트가 한국어로 답하면 엠대시(—), 마구 쓴 볼드, `결론적으로` 같은 맺음말, `~를 통해` 같은 번역투가 자주 섞입니다. 이 플러그인은 세션을 시작할 때 문체 규칙을 넣어 그런 표현을 처음부터 덜 쓰게 하고, 답변이 나온 뒤에는 검사기로 규칙 위반을 셉니다. 위반이 나온 답변은 에이전트가 서식을 고쳐 다시 냅니다.

에이전트에게 한국어 문서, 보고서, 메일, 커밋 본문을 자주 맡긴다면 쓸모가 큽니다. 지침만 적어 두면 금지한 부호도 계속 나오기 때문에 이 플러그인은 규칙을 알려 주는 일과 지켰는지 세는 일을 함께 맡습니다. 이 문서에서는 플러그인이 정한 한국어 문체 규칙 38항목을 보칙이라고 부릅니다. 검사 결과에도 이 이름이 나옵니다.

## 고치기 전과 후

에이전트가 흔히 내는 문장을 하나 지어 보았습니다.

> 결론적으로 캐시 설정을 조정하는 것이 중요합니다 — 이를 통해 응답 속도를 **크게** 개선할 수 있을 것입니다!

이 문장을 검사기에 넣으면 이렇게 나옵니다.

```
보칙 위반
  엠·엔 대시: 1건 (허용 0)
  느낌표: 1건 (허용 0)
```

엠대시와 느낌표는 한 번만 나와도 위반입니다. 이 문장에는 AI 글에 흔한 표현이 더 있습니다. 문장을 여는 `결론적으로`, 문장 끝에 버릇처럼 붙는 권고 `~하는 것이 중요합니다`, 번역투 `~를 통해`, 볼드, 가능과 추측을 겹친 `~할 수 있을 것입니다`입니다. 이런 표현은 한 답변에 한 번씩 나오는 정도면 허용 범위 안이고, 되풀이될 때만 검사기에 걸립니다.

답변 검사 훅은 내용은 두고 서식만 고치라고 지시합니다. 그래서 에이전트는 검사기가 짚은 두 곳만 고쳐 이렇게 다시 냅니다.

> 결론적으로 캐시 설정을 조정하는 것이 중요합니다. 이를 통해 응답 속도를 **크게** 개선할 수 있을 것입니다.

이 예문에서는 나머지 표현이 한 번씩만 나와 검사기에 걸리지 않습니다. 대신 세션에 넣은 보칙이 처음부터 그런 표현을 덜 쓰게 합니다. 보칙대로 썼다면 같은 내용이 이렇게 나옵니다.

> 캐시 설정을 조정하면 응답이 빨라질 수 있습니다.

두 경우 모두 원문에 없던 설정 이름, 수치, 원인은 넣지 않습니다. 보칙 38항이 그렇게 정해 두었습니다.

## 설치

### 필요한 것

파이썬 3.8 이상이 필요하고 표준 라이브러리만 씁니다. Claude Code의 훅은 모두 bash로 실행되고, Codex는 설치 스크립트와 세션 시작 훅에 bash를 씁니다. 그래서 Windows에서는 Git Bash가 있어야 합니다.

파이썬은 `python3`, `python`, `py -3`을 차례로 돌려 보고 되는 것을 쓰므로 `python3`이 없는 Windows에서도 작동합니다. Claude Code에서는 훅 래퍼가 실행될 때마다 고르고, Codex에서는 설치 스크립트가 처음 한 번 골라 명령에 적어 둡니다. bash로 실행되는 훅은 검사 결과의 한글이 깨지지 않도록 입출력을 UTF-8로 고정합니다.

### Claude Code

Claude Code 세션 안에서 아래 두 명령을 입력합니다.

```
/plugin marketplace add basilro/korean-style-guard
/plugin install korean-style-guard@korean-style-guard
```

터미널에서 설치하려면 같은 일을 CLI로 합니다.

```bash
claude plugin marketplace add basilro/korean-style-guard
claude plugin install korean-style-guard@korean-style-guard
```

설치는 다음에 여는 세션부터 적용됩니다. 갱신할 때는 마켓플레이스 목록을 먼저 받아야 최신 버전이 보입니다.

```bash
claude plugin marketplace update korean-style-guard
claude plugin update korean-style-guard
```

원격 저장소 대신 로컬 디렉터리를 마켓플레이스 소스로 등록하면 답변 검사 훅(`Stop` 훅)이 등록되지 않습니다. 로컬 소스로 개발하는 동안 답변 검사를 쓰려면 `hooks/settings-bridge.sh`를 `~/.claude/settings.json`의 `hooks.Stop`에 걸어 두세요. 이 스크립트는 설치된 플러그인 캐시에서 가장 높은 버전을 찾아 실행합니다. 캐시가 없으면 스크립트에 적힌 `$HOME/work/korean-style-guard`를 찾으므로 이 값을 자기 저장소 경로로 고칩니다.

### Codex CLI

Codex 플러그인에는 훅을 담을 수 없습니다. 그래서 Codex에서는 저장소를 받아 설치 스크립트를 실행합니다.

```bash
git clone https://github.com/basilro/korean-style-guard.git
cd korean-style-guard
codex/install.sh
```

설치 스크립트는 `ko-style` 스킬을 `$CODEX_HOME/skills/ko-style/`에 복사하고 `$CODEX_HOME/hooks.json`에 훅 네 개를 넣습니다. 세션을 시작할 때 보칙 본문과 예문 부록을 넣는 훅 둘, 답변을 검사하는 훅, 파일을 검사하는 훅입니다. `CODEX_HOME`을 지정하지 않으면 `~/.codex`를 쓰고, 그 폴더가 없으면 설치를 멈춥니다. 여러 번 실행해도 같은 훅이 겹쳐 들어가지 않습니다. 예전 판이 `python3`으로 등록해 둔 훅이 있으면, 이 스크립트가 그 명령을 이 컴퓨터에서 돌아가는 파이썬 명령(`python`, `py -3` 등)으로 고칩니다.

세션 시작 훅 둘은 bash로 `hooks/inject-rules.sh`를 부르고, 답변 검사 훅과 파일 검사 훅은 설치할 때 고른 파이썬으로 `scripts/stop_hook.py`와 `scripts/post_write_hook.py`를 바로 부릅니다.

훅은 받은 저장소 안의 스크립트를 절대 경로로 부릅니다. 그래서 설치한 뒤에 저장소 폴더를 지우거나 옮기면 훅이 작동하지 않습니다.

설치가 끝나도 훅은 바로 실행되지 않습니다. Codex를 실행해 `/hooks`에서 설치 스크립트가 넣은 훅 네 개를 모두 신뢰(trust)로 승인해야 합니다.

훅을 손으로 넣고 싶다면 `codex/hooks.example.json`을 참고해 `$CODEX_HOME/hooks.json`이나 `<repo>/.codex/hooks.json`에 적습니다. 이때 경로는 절대 경로로 씁니다. 이 예시는 실행 시점, 적용할 도구(matcher), 제한 시간이 설치 스크립트가 넣는 훅과 같습니다. 다른 점은 명령입니다. 설치 스크립트는 설치할 때 파이썬을 한 번 골라 검사 스크립트를 바로 부르고, 예시는 bash 래퍼(`hooks/check-output.sh`, `hooks/check-written-file.sh`)를 불러 실행할 때마다 파이썬을 찾습니다.

## 쓰는 법

설치를 마치면 답변 검사와 파일 검사는 따로 부르지 않아도 실행됩니다. 아래는 사용자가 직접 고르거나 실행하는 기능입니다.

### 답변 문체 켜기

output style은 Claude Code에서 답변 문체를 바꾸는 설정입니다. 이 플러그인의 `korean-style-guard:korean-style`은 답을 처음부터 보칙에 맞게 쓰는 순서를 담고 있어서 답변 검사에 걸리는 일을 줄여 줍니다. `/output-style`에서 고르면 켜집니다. 이 문체 파일(`output-styles/korean-style.md`)은 맨 위 설정(frontmatter)에 `keep-coding-instructions: true`를 두어 Claude Code의 기본 코딩 지침을 그대로 남깁니다. 사용자가 고른 다른 문체를 덮어쓰는 `force-for-plugin`은 쓰지 않습니다.

### 이미 쓴 글 점검하기

이미 쓴 글을 점검하고 고칠 때는 `ko-style` 스킬을 씁니다. Claude Code에서는 `/ko-check [파일]` 명령이 이 스킬로 파일을 검사해 결과를 표로 보여 주고, 고칠지는 사용자에게 묻습니다. 파일을 주지 않으면 이번 대화에서 방금 쓰거나 고친 한국어 문서를 대상으로 삼습니다. Codex에서는 `$ko-style`로 스킬을 부릅니다.

### 검사기를 따로 실행하기

훅 없이 따로 실행할 수 있는 검사기는 셋입니다. 문서에서 보칙 위반을 세는 산문 검사기, 코드에 한글 이름이 섞였는지 보는 이름 검사기, 한국어 질문에 영어로 답했는지 보는 언어 판정기입니다.

```bash
python3 scripts/ko_style_check.py 파일.md
cat 파일.md | python3 scripts/ko_style_check.py --json
python3 scripts/ko_identifier_check.py 파일.cs
python3 scripts/ko_identifier_check.py 파일.tsx --json
python3 scripts/ko_lang_check.py 질문.txt 답변.txt
```

경로는 저장소를 받은 폴더 기준입니다. 마켓플레이스로 설치했다면 `~/.claude/plugins/cache/korean-style-guard/` 아래 버전 폴더에 같은 스크립트가 있습니다. `python3`이 없는 환경에서는 `python`이나 `py -3`으로 바꿔 씁니다. Windows에서 출력의 한글이 깨지면 명령 앞에 `PYTHONIOENCODING=utf-8`을 붙입니다.

산문 검사기는 파일이나 표준 입력을 받습니다. 위반이 없으면 `보칙 위반 없음`을 출력하고 종료 코드 0으로 끝납니다. 위반이 있으면 항목마다 찾은 개수와 허용 개수를 보여 주고 1로 끝납니다. `--json`을 붙이면 위반 목록과 함께 항목별 개수(`counts`)가 나옵니다.

이름 검사기는 확장자로 언어를 알아내므로 파일 경로를 꼭 줘야 하고, 주지 않으면 종료 코드 2로 끝납니다. 통과하면 `한글로 된 이름 없음`을 출력하고 0으로 끝나며, 한글 이름이 있으면 행 번호와 이름을 보여 주고 1로 끝납니다. 검사하는 언어가 아니면 `검사 대상 언어가 아닙니다`를 출력하고 0으로 끝납니다.

언어 판정기는 질문 파일과 답변 파일을 받아 판정 결과를 JSON 한 줄로 출력합니다. 영어 답변으로 판정하면 `flagged`가 `true`입니다.

### 검사 끄기

검사가 작업과 맞지 않을 때는 환경 변수로 끌 수 있습니다. 에이전트를 실행하는 셸에 지정하거나, Claude Code라면 `settings.json`의 `env`에 적습니다.

| 변수 | 끄는 것 |
|---|---|
| `KO_STYLE_SKIP_LANG=1` | 답변 검사 가운데 언어 판정만 |
| `KO_STYLE_SKIP_FILES=1` | 파일 검사 훅 전체 |
| `KO_STYLE_SKIP_IDENTIFIERS=1` | 파일 검사 가운데 이름 검사만 |

`KO_STYLE_SKIP_LANG`은 값을 `1`로 줄 때만 언어 판정을 끕니다. 나머지 두 변수는 빈 값만 아니면 어떤 값을 넣어도 해당 검사를 끕니다. `0`을 넣어도 꺼지므로, 다시 켜려면 변수를 지워야 합니다. 이름 검사를 끄는 변수는 프로젝트가 원래 한글 이름을 쓰는 경우를 위해 두었습니다.

## 무엇을 잡나

보칙 38항목은 여덟 묶음으로 나뉩니다. 전체 문구는 `rules/ko-style-rules.md`에, 고칠 것과 둘 것을 견준 예문은 `rules/ko-style-examples.md`에 있습니다. 검사기는 이 가운데 기계로 셀 수 있는 표현을 세고 항목마다 허용 개수를 둡니다. 허용 개수가 0이면 한 번만 나와도 위반입니다.

| 묶음 | 항목 | 대표 예 |
|---|---|---|
| 서식 | 1~4 | 엠대시, 문장을 감싼 볼드, `**라벨**:`, 이모지와 느낌표, 연결어미 뒤에 버릇처럼 찍는 쉼표 |
| 문장 | 5~7 | `확인 완료.`처럼 서술어 없는 문장, `A가 아니라 B` 되풀이, `~하는 것이 좋습니다` 꼬리 |
| 구조 | 8~12 | `세 가지 방법` 헤딩, `X: Y` 부제, `정리해 드리겠습니다` 예고, 묻지 않은 후속 제안 |
| 어휘 | 13~18 | `핵심은 X입니다`, `결론적으로`, `단순한 X를 넘어`, `청사진`, 끝머리의 `향후` |
| 번역투 | 19~24 | `~에 대해`, `~를 통해`, `인자를 가지고 있다`, `되어지다`, `여러 파일들`, `그것` |
| 우리말 다듬기 | 25~30 | `-적`과 `에서의`, `소개시키다`, `-었었-`, `~을 요하다`, `미리 예약`, `매우` |
| 높임과 조사와 띄어쓰기 | 31~37 | `~하지 않으면 안 된다`, `커피 나오셨습니다`, 말투 섞기, `할수있다`, 영어 답변 |
| 과잉 교정 방지 | 38 | 지키느라 글을 밋밋하게 만들거나 사실과 서법을 바꾸는 일 |

1~37항은 대부분 금지 규칙이라 지나치게 지키면 글이 밋밋해집니다. 38항은 이런 과잉 교정을 막으려고 두었습니다. 이 항은 과장과 광고체만 지우고 구체성은 남기게 합니다. 고칠 때는 추측을 단정으로 바꾸지 않고, 한 표현을 지우면서 다른 버릇을 새로 만들지 않습니다.

사람 글에도 흔한 표현은 0건을 요구하지 않고 되풀이만 셉니다. 연결어미 뒤 쉼표는 짧은 답변에 넷까지, 긴 글은 500자에 하나까지 허용합니다. 번역투 조사 구는 셋까지(긴 글은 800자에 하나), 강조 부사는 둘까지(긴 글은 1,000자에 하나) 둡니다. 정상 용법은 세지 않습니다. 예를 들면 다음과 같습니다.

- `목적`, `지적`처럼 `-적` 앞이 한 음절인 낱말
- `회의`처럼 `의`로 끝나는 명사에 조사 `의`가 붙은 꼴(`회의의 결과`)
- `이해시키다`처럼 실제로 남에게 시키는 뜻의 `-시키다`
- 회계 용어 `자본잠식`

1.12.0에서는 글을 읽기 쉽게 하는 검사를 더했습니다. `효과적입니다`처럼 평가하는 말로만 닫는 문장은 둘까지 허용하고, 다음 표현은 한 번도 허용하지 않습니다.

- 판단 기준을 `~에서 갈립니다`처럼 동사 하나로 뭉뚱그린 문장
- 누구의 견해인지 밝히지 않고 `~다고 봅니다`로 맺는 문장
- `~하시기를 권합니다`처럼 판에 박힌 권고
- 산문에서 `~하세요`로 끝나는 문장이 셋 잇달아 나오는 경우
- `확실한 건 이 정도예요`처럼 답이 얼마나 확실한지를 따로 해명하는 문장
- 본문에 없는 구절을 따옴표로 가리키는 문장
- 글 끝에 따로 붙인 `오늘 저녁에 ~하세요` 같은 명령
- 한 문장에 `~는 점`을 셋 이상 늘어놓은 나열

문장 사이를 잇는 말이 하나도 없는 글, 한 목록 안에 끝맺음(`~하세요`와 `~합니다`)이 섞인 경우, 목록 앞에 붙는 `다음 순서로 진행합니다` 같은 틀은 위반으로 보고하지 않고 `--json`의 `counts`에만 남깁니다. 답의 말씨(합니다체, 해요체)가 질문과 맞는지도 보지 않습니다. 산문 검사기에는 질문이 전달되지 않습니다. 게다가 해요체로 물었어도 메일이나 공문을 부탁했다면 합니다체로 쓰는 편이 맞습니다.

## 어떻게 동작하나

플러그인은 세 시점에 끼어듭니다.

| 시점 | 실행되는 것 | 하는 일 |
|---|---|---|
| 세션 시작, `/clear`, 대화 압축 뒤 | `hooks/inject-rules.sh` | 보칙 본문과 예문 부록을 세션 맥락에 넣음 |
| 답변을 마칠 때 | `hooks/check-output.sh` | 답변 언어를 판정하고 보칙 위반을 세어 걸리면 다시 쓰게 함 |
| `Write`, `Edit` 도구로 파일을 쓴 뒤 | `hooks/check-written-file.sh` | 방금 쓴 문서나 코드 파일을 검사함 |

세션이 시작되면 보칙 본문(`rules/ko-style-rules.md`)과 보칙 항목 번호대로 정리한 예문 부록(`rules/ko-style-examples.md`)이 두 훅으로 나뉘어 들어갑니다. 플러그인에는 CLAUDE.md 같은 파일을 배포할 길이 없습니다. 대신 세션 시작 훅이 돌려주는 글(`additionalContext`)이 세션 맥락에 들어가므로 이 길로 보칙을 넣습니다. 이 글은 훅 하나마다 10,000자에서 잘리기 때문에 보칙을 두 파일로 나눴습니다. output style은 메인 대화에만 적용되고 서브에이전트, 헤드리스 실행, cron에는 걸리지 않으므로 보칙을 넣는 일은 이 훅이 맡습니다.

답변이 끝나면 검사가 두 단계로 진행됩니다. 먼저 한국어로 물은 질문에 영어로 답했는지 보고, 다음으로 한국어 답변이 보칙을 지켰는지 셉니다. 걸린 것이 있으면 훅이 답변을 에이전트에게 돌려보냅니다. 영어로 답했다면 한국어로 다시 쓰라고 하고, 보칙을 어겼다면 걸린 항목 목록을 주며 내용은 두고 서식만 고치라고 합니다. 고친 답변은 다시 검사하지 않으므로 검사와 수정이 끝없이 되풀이되지 않습니다.

도구로 쓴 파일은 답변 검사가 보지 못하므로 파일 검사 훅이 따로 맡습니다. 문서 파일에는 산문 검사기를, 코드 파일에는 이름 검사기를 씁니다. 보칙 첫머리는 프로젝트 관례가 없으면 식별자, 딕셔너리 키, 열거형 값, 파일명을 영문으로 쓰라고 정합니다. 지침만으로는 잘 지켜지지 않아 이름 검사기를 붙였습니다.

### 언어 판정

언어 판정은 멀쩡한 답변을 막지 않도록 기준을 넉넉하게 두었습니다. 훅 입력에는 사용자 질문이 없으므로 대화 기록 파일(`transcript_path`)에서 마지막 사람 입력을 찾고, 도구 결과와 훅이 덧붙인 꼬리표(`<system-reminder>` 등)는 건너뜁니다. 질문과 답변 모두 코드 블록, 인라인 코드, 인용, URL, 경로, 파일명, 식별자, 약어를 빼고 셉니다.

질문은 한글이 든 줄만 모아 한글 단어가 30% 이상일 때 한국어 질문으로 봅니다. `What is 눈치?`처럼 영어 문장에 한글 단어가 하나만 섞인 질문은 한국어 질문으로 보지 않습니다. 답변은 영어 산문 단어가 12개 이상이고 그 비율이 60% 이상일 때만 막습니다. 다음 질문에는 영어 답변이 맞으므로 판정하지 않습니다.

- 영어 답변이나 번역을 바라는 질문(`영어로`, `번역해 줘`, `translate`). 다만 `한국어로 번역해 줘`처럼 방향이 한국어면 판정함
- 영어 글을 다듬어 달라는 질문
- 커밋 메시지, README, PR 설명, 릴리스 노트를 써 달라는 질문

이런 요청 표현은 사람이 친 한글 줄에서만 찾습니다. 그래서 붙여 넣은 영어 문서 안의 `translation`은 요청으로 치지 않습니다. 한글 줄에 있더라도 `영어로 된 문서`처럼 문서를 설명하는 말은 요청이 아니므로 판정합니다.

### 파일 검사 범위

산문 검사는 확장자가 `.md`, `.markdown`, `.mdx`, `.txt`, `.rst`이고 한글 비율이 15% 이상이며 100자 이상인 파일만 봅니다.

이름 검사는 파이썬, 자바스크립트 계열, 자바, 코틀린, 스위프트, 다트, C, C++, C#, Go, Rust, PHP, Ruby, SQL 파일을 봅니다. 주석과 문자열 리터럴을 지운 코드에서만 한글을 찾고, 화면에 보이는 글을 잘못 잡지 않도록 JSX 텍스트, 문자열 보간, 정규식 리터럴을 따로 다룹니다. 실제 코드베이스 936개 파일에서 잘못 잡은 곳은 2건이었습니다. 문자열 안은 보지 않으므로 `{"이름": 1}` 같은 한글 딕셔너리 키는 놓칩니다. 문자열까지 보면 화면에 보이는 글을 잘못 잡게 되고, 그러면 사용자가 훅을 꺼 버릴 수 있어서 놓치는 쪽을 골랐습니다.

두 검사 모두 `.git`, `node_modules`, `vendor`, `dist`, `build` 같은 폴더 아래 파일은 건너뜁니다.

## 근거

항목을 넣거나 허용 개수를 정할 때는 사람 글과 AI 답변에 같은 검사기를 실행해 빈도를 견줬습니다. 사람 글로는 국어학 논문 본문 35만 자, AI 글이 퍼지기 전인 2022년 말 판 한국어 위키백과 문서 65편, 웹소설 완결작 40편 이상에서 뽑은 문장을 썼습니다. AI 쪽은 기본 말투로 쓴 답변 표본 122편(8만 3천 자)입니다.

아래 표는 AI 표본과 사람 논문의 10만 자당 건수를 견준 값으로, 4, 6, 7, 13~15항의 근거입니다. 9항(콜론 부제 헤딩)은 논문에 마크다운 헤딩이 없어 견주지 못했습니다. 16~18항은 양쪽 표본 모두에서 거의 나오지 않아 빈도로는 근거를 대지 못했습니다. 그래도 과장을 지우라는 38항과 취지가 같아 항목을 남겼습니다.

| 항목 | AI 표본 | 사람 논문 | 배수 |
|---|---|---|---|
| 분열문 강조(13항) | 10.9 | 0.6 | 약 18배 |
| 결산 표지(14항) | 29.0 | 3.1 | 약 9배 |
| 당위로 끝나는 문단(7항) | 12.1 | 1.4 | 약 9배 |
| 범위 상승(15항) | 3.6 | 0 | 사람 0건 |
| 연결어미 뒤 쉼표(4항) | 159.6 | 102.5 | 1.6배 |
| 부정 대구(6항) | 21.8 | 14.1 | 1.5배 |

번역투 조사 구와 `-적`, `-의` 같은 표현은 오히려 사람 글에 더 많이 나왔습니다. 사람도 번역투를 많이 쓴다는 뜻일 뿐, 이 표현이 자연스럽다는 근거는 아닙니다. 그래서 이 묶음은 빈도 차이 대신 국어학과 번역학의 연구, 교정 교열 책을 근거로 삼습니다. 사람 글에도 흔한 조사 구와 `-적`은 되풀이될 때만 세고, 이중 피동, 불필요한 `-시키다`, 번역투 관용구, 겹말, `-의` 연쇄는 한 번만 나와도 셉니다. 높임과 조사와 띄어쓰기 묶음 가운데 31~36항은 국어학 논문에서 근거가 선 것만 넣었습니다.

1.12.0이 실제로 읽기 쉬워졌는지는 블라인드 시험으로 쟀습니다. 같은 질문 12개에 1.11.0 보칙과 새 보칙으로 각각 답하게 하고, 어느 버전인지 모르는 심사자 둘이 사람 말투, 이해, 뜻(내용이 정확하고 쓸모 있는지)을 1~5점으로 매겼습니다. 시험은 여섯 번 했습니다. 처음 세 번은 같은 질문을 썼는데, 둘째와 셋째에는 보칙 예문 일부가 그 질문에서 나와 결과를 믿기 어려웠습니다. 넷째부터는 매번 새 질문을 썼습니다. 넷째 결과는 다섯째 시험 전에 보칙을 고치는 데 썼으므로 공정한 비교가 되지 못합니다. 그래서 `docs/references.md`의 결과 표에는 다섯째와 여섯째 시험만 실었습니다. 두 번 모두 새 버전이 더 많은 문항에서 이겼고 세 점수가 모두 올랐습니다. 처음에는 다시 읽어야 하는 문장을 1.11.0의 절반 이하로 줄이는 것도 목표로 삼았는데, 이 목표는 이루지 못했습니다. 남은 문장에는 사실 오류처럼 내용의 문제가 많았고, 문항 12개를 한 번씩만 비교해 결과의 흔들림도 큽니다.

말뭉치별 수치, 시험 결과 표, 참고 문헌 서지는 `docs/references.md`에 모았습니다.

## 개발과 시험

시험은 `tests/run_all.py` 하나로 모두 실행합니다.

```bash
python3 tests/run_all.py
```

이 명령은 다섯 시험 묶음을 차례로 실행합니다. 산문 검사기 회귀 시험, 언어 판정기 회귀 시험, 이름 검사기 시험이 셋이고, 나머지 둘은 검사기를 속이려고 짠 입력입니다. 언어 판정기 쪽 31건은 막지 말아야 할 답변 22건과 막아야 할 영어 답변 9건이고, 산문 검사기 쪽 33건은 하나도 걸리면 안 되는 바른 한국어 문장입니다. 이름 검사기 시험은 `tests/cases/`에 사례 30개를 둡니다. 여기에는 JSX의 화면 글, 문자열 보간, 이스케이프를 해석하지 않는 문자열(C#의 `"""` 원시 문자열 등), 정규식 리터럴처럼 지우기 까다로운 코드와 문법이 깨진 파일이 들어 있습니다. 사례마다 기대값과 이유는 `tests/expected.txt`에 적었습니다.

시험 묶음이 끝나면 저장소 상태도 확인합니다.

- `skills/ko-style/scripts/`의 사본이 `scripts/` 원본과 같은지(어긋나면 `ko-style` 스킬이 옛 규칙으로 검사함)
- 이 README와 보칙, 예문 부록, 스킬, output style, 명령 문서가 보칙을 지키는지
- `hooks.json`이 부르는 보칙 파일마다 9,800자를 넘지 않는지(세션 맥락에 넣을 수 있는 10,000자에 여유를 둔 값)
- `plugin.json`의 output style 경로가 있는지
- `tests/samples/`의 실제 문장 표본에서 잘못 잡거나 놓친 항목이 없는지
- 공백 없는 긴 입력에서도 검사가 2초 안에 끝나는지(답변 검사 훅의 제한 시간은 15초)
